# M58 真实 TraX 通信验收与初始化文字索引精度修正

VOT toolkit 0.7.1 客户端与 TraX 4.0.2 服务端的真实管道通信已通过 CPU 合成测试。发现并修正的是**离线初始化文字索引准备中的坐标精度假设**；实际模型构建和 bundle 校验在这项测试中被替换为确定性 CPU 记录器，因此没有新的模型跟踪结果、语言收益或正式 VOT 指标。

## 修正了什么

此前 evaluation_preparation 的 CPU 检查覆盖 TraX Rectangle 构造器，却没有走完整收发。`vot_wire_bbox` 当时只复现 float32 存储。真实通信还把每个坐标写成四位小数，再由接收端读成 float32：

```text
toolkit xywh → float32 → 四位小数协议文本 → 接收端 float32
```

例如初始化 x=1.123456789，仅经过构造器会成为 1.1234568357467651；实际协议发送 1.1235，服务端收到 1.1234999895095825。旧准备方式与实际收到的框生成不同的文字键。同一张图、同一个高精度原框，使用旧索引在真实入口中触发 KeyError；包含完整转换的索引正常匹配。

本页补充并修正交接文档 **§5.89** 和 evaluation_preparation 中对该辅助函数的解释。其 153 次构造器检查仍是已完成的历史事实，不能解释成 153 次完整 TraX 通信验收。原先 [1.1,2.2,30.3,40.4] 的例子本来只有一位小数，没有暴露四位小数这一步。

新增 `corrected_test/vot_rectangle_transport.py` 是未来 VOT 文字输入准备应使用的独立辅助函数，输入应先经过 toolkit 实际采用的 region→xywh 转换。运行时继续按实际接收的框精确查文字，不改变模型框，不增加模糊匹配。原冻结六个接口文件不改动，旧辅助函数保留为历史绑定；不能继续将它用作完整 VOT 文字索引转换。OPE 坐标和六位小数结果文件不受此修正影响。

当前没有生成过 M58 正式 VOT 文字银行，也没有证据用这个新入口准备问题解释此前 SUTrack/STTrack 的分数差异。

## 实际测试与结果

| 真实客户端/服务端通信 | 结果 |
| --- | --- |
| 第一个高精度初始化框，正确索引 | 初始化及两次逐帧报告通过 |
| 同一张初始化图片，第二个不同目标框 | 取得另一份文字，初始化及两次报告通过 |
| 未登记的初始化框 | 在模型初始化前拒绝，预期 KeyError |
| 同一个高精度框，仅按构造器精度建立旧索引 | 在模型初始化前拒绝，预期 KeyError |

四个会话共完成四次确定性预测报告；RGB/Depth 双通道顺序、初始化帧与后续帧顺序、实际传输框及置信度均检查。客户端读取的预测框与完整协议转换一致，置信度未经过应用层重映射。四位小数是 TraX 本身的协议行为，不是新加的跟踪框修正策略。

初次测试只预期 float32，因此在第一个预测报告的框比较处失败，`initial_test/transport.exit=1` 和原日志完整保存。随后采用完整转换，并加入同一高精度框的新旧索引对照；修正测试 `corrected_test/transport.exit=0`。两个负例的服务端退出码 1 是预设的拒绝结果，与整个测试的成功退出码 0 区分。

实际运行的是 toolkit TrackerProcess、原 semantic VOT 循环、M39 bridge、原 RGB-D 解码和 InitializationTextBank。仅模型工厂、bundle 检查和文字银行工厂边界被替换；银行本身及其 SHA/键查找是真实代码。图片由脚本生成，共三张 RGB JPEG、三张 uint16 Depth PNG；文字向量为确定性合成向量。GPU 初始化、模型权重加载、数据集图片读取、真实模型 track 和优化均为零。耗时约 8.36 秒。

该检查使用实际安装的 TraX 4.0.2；没有声称覆盖其他版本、所有 region 类型或所有数值边界。后续正式 VOT 前仍需在最终固定权重上核对真实 GPU 入口轨迹，不能用 CPU 记录器替代模型验收。
